# 阶段一 一个任务包与一次完整回合的手工走查

日期 2026-10-15
状态 已完成
原始证据 `RECORD/phase1/` 下三次 episode 的原始流、差异、判分
任务包 `tasks/t01_keyword_summary/` 与 `tasks/t02_trimmed_mean/`
用到的脚本 `harness/phase1_prompts.py` 与 `harness/phase1_run.py`

## 一、为什么要做这一条

阶段计划把先手工后自动化定为硬性顺序。理由是命令行智能体的行为差异极容易被误判成自己脚手架的缺陷，一旦这种误判混进正式运行，追查代价很高。因此先用两个任务把首轮、判分、改动统计三步在真实任务上走一遍，把单回合的真实成本与时长量到。

## 二、方法

两个任务包都用同一套办法造。先写一份全绿的实现与可见测试，跑通后反向改坏，改动本身存为注入补丁，其逐行取反即参考补丁。这样参考补丁与注入补丁由构造互逆，不需要人工维护两份文本。`t01` 的往来一致性已单独核对，把注入补丁打上再撤销，得到的文件与干净版逐字节相同。

`t01` 是词频统计，缺陷在排序键与排序方向两处协同出错，同次时未按词形升序。`t02` 是截尾均值，缺陷在截尾个数用了四舍五入而非向下取整，以及切片区间的负下标写法在截尾个数为零时退化为空区间。两者的参考补丁都是两行改动，即 `L_gold` 等于四。

工作区建立在项目树之外的 ASCII 路径下，各是一份带单次提交的 git 仓库，提交内容为注入缺陷之后的起点状态，`core.autocrlf` 显式设为假。提示词由 `harness/phase1_prompts.py` 渲染，五份二轮提示词共用同一份失败信息，脚本断言行除第一行外完全相同，该断言已通过。首轮提示词保持中性，不含最小化要求。

判分一律由脚手架执行，不采信模型自述。可见测试与隐藏测试分别执行，隐藏测试只在判分时复制进工作区，跑完即删。

## 四、五条结论

**一，全流程走通，成本与时长量准。** 单次零到十二美分之间，耗时二十二到二十七秒，均低于阶段二文档所给的下界之上限。三百秒墙钟留有十倍以上余量。

**二，首轮全部一次通过，这是本次最重要的发现。** 三次 episode 无一失败，`M_fail` 为零。三次的 `L_model` 都恰好等于 `L_gold` 等于四，`EditRatio` 都为一。也就是说在没有任何用户反馈的条件下，模型每次给出的都是参考最小补丁本身，既不多改也不少改。

**三，可见测试在工作区内可读，这抵消了收紧失败信息的做法。** 提高首轮难度的直觉做法是少给一些失败信息，只给失败的用例名而不给断言详情。这条路走不通，因为可见测试文件就在工作区里，模型用读取工具就能复原全部期望值。`t02` 的失败信息里带出了空序列的报错原文与断言两侧的取值，模型仍然读了四个文件才动手，说明它的行为是读懂代码而不是照抄断言。难度只能来自任务结构本身，不能来自隐瞒信息。

**四，失败信息必须以 UTF-8 落进提示词，否则中文报错会变成乱码。** `t02` 的实现里有一处抛 `ValueError` 并带中文说明。按默认设置执行 pytest，该说明在管道里被写成替换字符，进入提示词就是乱码。加上 `PYTHONUTF8` 与 `PYTHONIOENCODING` 两项后恢复正常。两相对照已实测确认。这条对正式脚手架是硬约束，`agent.py` 的子进程环境已含这两项。

**五，阶段零关于固定开销的判断需要修正。** 阶段零记下能运行测试那一臂耗时约为另一臂的二点六倍，并推测存在一项固定额外开销。在真实任务上这个差距收窄到一点二倍，二十六点九秒对二十二点二秒，而且能运行测试那一臂的回合数反而更少，九对十一，成本也更低。可见二点六倍更像是玩具任务的基线过短所致，玩具任务的不能运行那一臂有四次落在十秒上下。此处只有一对真实任务的观测，尚不足以定论，但三百秒超时被挤占的担忧可以降低。

## 五、与阶段零结论的出入

阶段零的改代码路径核验在两个只有几行的玩具形状上得到两个参数量级的判断，本次在真实任务上重做，结论方向一致但差距缩小，已记入上一条。其余三条结论在本次得到复现。模型仍然只在编辑工具里改文件，`can_run` 臂仍然先跑一条目录列举再跑测试，非测试类命令恰好占已执行命令的一半。

## 六、遗留

1. 分支未走通。三次首轮全绿，按阶段计划的流程分支不触发。分支起点哈希相等这条断言要等到阶段三由脚手架与假模型验证，阶段一未能覆盖。
2. 只有三次观测，且都在一个模型上。首轮失败率的真值仍需在阶段四按任务逐项量出。
3. 两个任务包的规模偏小，实现与测试合计都在四五十行。是否需要更长的任务才能把首轮失败率抬起来，留待阶段二定造题规范时决定。
