# 任务包与反向补丁

日期 2026-10-15

## 一个任务包里装了什么

本实验的每个任务都是一个自带答案的小项目。除了要被修的那段有缺陷的代码，它还要带四样东西。

1. 可见测试。这是模型能看到也能运行的测试，也就是失败信息的来源。
2. 隐藏测试。模型看不到，只在判分时使用。它的作用是挡住把可见测试的期望值写死进代码的做法。
3. 注入补丁。把干净实现改成有缺陷实现的那份改动。
4. 参考补丁，也叫金补丁。就是这道题的最小正确解法，用于计算过度修改比。

## 为什么参考补丁不手写

一份手写的参考补丁很难保证真的只有两行。人写的时候容易顺手改个空行、动个注释，而过度修改比的分子分母对这个极其敏感。

本实验的做法是先写干净实现，再把它改坏。这个改坏的改动就是注入补丁，逐行取反就是参考补丁。两份文本由构造保证互逆，不需要人工维护两处一致。核验办法也简单，把注入补丁打上再撤销，得到的文件应当与干净实现逐字节相同。`t01` 已经这样核对过。

## 工作区为什么要是 git 仓库

模型改了哪些行、改了几个文件，都要有客观来源。做法是把注入缺陷之后的起点状态提交一次，模型改完之后用 `git diff` 对着这次提交统计。这样既不需要解析模型的自述，也不需要给每个文件算哈希。

有一个坑必须提前堵上。本机系统级的 git 配置把 `core.autocrlf` 设成了真，检出时会把行尾换成 Windows 风格。这样一来同一份代码在不同机器上算出的行数可能不同，逐字节比较也会失败。所以工作区仓库要显式把 `core.autocrlf` 设成假，仓库根目录再放一份 `.gitattributes` 钉死行尾。

## 一轮是什么

`claude -p` 一次调用，就是一个用户回合，也就是本实验定义的一轮。命令行工具没有参数可以限制模型在这一次调用里自己迭代几轮，所以一轮的长短由三百秒墙钟、工具白名单和提示词共同约束。这个定义要原样写进报告，否则读者无法复现。

## 为什么指标要分两轮记

第二轮的修改规模不能跟第一轮直接比，因为第二轮要干的活已经少了一块，改动的行数自然更少。跨条件比较才是有意义的，因为五个条件的第二轮起点逐字节相同。
